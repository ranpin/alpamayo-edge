# 驾驶域 OOD 场景评测集（闸门 3 产物，2026-07-31）

**n=184，八分类多选，随机基线 12.5%。** 标答来自 NVIDIA 自己的**人工核验**标注。

这份评测集存在的意义：在此之前本项目**全部精度证据都来自具身机器人操作**
（robovqa/robofail，"机器人有没有打开抽屉"），而项目标题是自动驾驶——
这是任何懂行的人的第一问。这是第一份驾驶域的带标答证据。

## 来源与为什么是它

| 候选 | 判定 |
|---|---|
| **`nvidia/PhysicalAI-Autonomous-Vehicles :: reasoning/ood_reasoning.parquet`** | ✅ **采用**。**人工核验**，卡片原话 "intended to support Vision-Language-Action (VLA) model evaluation"；与 Cosmos/Alpamayo 同厂商同体系 |
| 同仓库 `labels/obstacle.offline` | ❌ 卡片明确写 **"autogenerated (non-GT) machine labels"** ⇒ 拿它当 ground truth 等于把伪标签当标答 |
| `dgural/PhysicalAI-Autonomous-Vehicles-Sample`（公开） | ❌ 只有 700 个 mp4，`samples.json` 里**零标注**（实测：仅 filepath/uuid/group/tags） |
| `KevinNotSmile/nuscenes-qa-mini`（公开） | ⚠️ 备选。真实 6 路环视 + QA 标答，但图被上传者**预缩到 224×224**（低于本项目 448 基准）⇒ **撑不起分辨率 Pareto** |
| `EPFL-DrivingVQA`（公开） | ⚠️ 备选。原生 1600×1063 + 多选标答，但是**驾照考题实拍**、非 AV 传感器分布 |

## 任务设计（三个都是为了让分数可信）

**① 类别平衡。** 原始 9 类严重不均衡——`WORK_ZONES` 占 49.2%。直接用全量的话，
"永远答 work zone" 就能拿 49.2%，分数无法解读。故每类取 23 个（= 最小类的全部）。

**② 排除 `OTHER_LONGTAIL`。** 它是**无正面定义的兜底类**，要求模型选它是 ill-posed。
去掉后 8 类 × 23 = **n=184**，随机基线 **12.5%**。

**③ 答案字母精确配平。** 初版每题独立随机打乱选项，结果 184 题的答案字母落在 **15–30**
之间 ⇒ 恒选出现最多的字母能拿 **16.3%**，高于名义基线。改为先构造"每字母恰好 23 次"
的目标表再整体打乱，实测配平后 **A–H 各 23（12.5%）**，且 (类别, 字母) 最大格 7/23
⇒ 无"类别↔字母"捷径。

## 规格

- 相机：`camera_front_wide_120fov`（该标注子集全部是这一路）
- **原生 1920×1080 HEVC 30 fps / 20.17 s / 605 帧**（与闸门 2 公开 sample 实测规格一致）
- 每 clip 均匀采 **6 帧**、**原生分辨率不缩放**（口径同 `eval/vision/av_frames/README.md`）
- split 分布：train 154 / val 30（沿用上游标注自带的划分字段，未自行重划）

⇒ 因为存的是原生帧，**同一批数据可同时支撑精度评测与分辨率 Pareto**
（原生 2040 token/帧 ⇒ `engines/*_len4096` 实装 1 帧；缩到长边 448 则 112 token/帧）。

## 帧不入 git

`frames/`（184 clip × 6 帧 ≈ **190 MB**）已 gitignore。它是**可重建大件**：
`manifest.json` 钉住了每个 `clip_id` 与答案，脚本按固定种子确定性重建。

```bash
export HF_TOKEN=...        # 需对 gated 数据集有权限的 token
.venv/bin/python alpamayo-edge/data/harvest_ood_eval.py \
    --out alpamayo-edge/data/ood_eval --per-class 23      # 种子默认 20260731
```

## 取帧为什么不整块下载

1740 个 OOD clip 散落在 **1085 个 chunk**，每个 camera chunk zip ≈ **1.14 GB**
⇒ 整块下载 ≈ **1.4 TB**（本机当时只剩 18 GB）。

HF 支持 range request，故用 `HfFileSystem` + `zipfile` **只读中央目录再抽单个成员**：

```
zip 1.14 GB → 中央目录 3.8 s（291 成员 / 97 个 mp4）→ 抽 1 个 mp4 14.65 MB / 5.5 s
```

实测每 clip ≈ 10 s、磁盘瞬时 ~15 MB。**184 clip 全量 0 失败**，产出 190 MB。
脚本带 resume 快路径：帧已在本地的 chunk 完全不碰网络（重建 manifest 仅 **4.1 s**，
而不是重开 175 个 zip 的 ~12 分钟）。

## 诚实边界

- **标注是"事件聚类"而非逐帧感知标签**：标的是整段 clip 最具安全相关性的场景类别，
  因此这测的是**场景级理解**，不是目标检测精度。
- **train 占多数（154/30）**：Cosmos-Reason2 的训练是否见过这些 clip 无法排除
  （NVIDIA 未公开 CR2 的训练集清单）⇒ 不能声称是"未见过数据"。这是**跨精度对照**
  实验（同帧同题比 FP16/INT8/INT4），该风险对三个精度同等作用，不影响掉点结论；
  但**不可**用来声称模型的绝对场景理解能力。
- **n=184 的统计功效**：与既有 n=210 同量级 ⇒ MDE 仍在 ~7 pts 量级，
  小于该量级的掉点测不出来（见 `docs/PROBLEMS.md` H 节与 `TASK_METRICS.json`）。
